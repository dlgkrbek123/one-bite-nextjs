페이지 라우터 버전에서는 페이지 컴포넌트에서 아래의 항목을 정의하여 데이터페칭을 수행
- props를 페이지 컴포넌트에 전달 => props drilling
- 모두 클라이언트 컴포넌트였기떄문에 컴포넌트에서 fetch하면 양쪽에서 실행되므로
  별도의 함수의 도움을 받음

export default function getServerSideProps() {}
export default function getStaticProps() {}
export default function getStaticPaths() {}

앱 라우터에서는 서버 컴포넌트가 있으니까 컴포넌트 함수를 async로 선언하고 await를 내부에 작성
각 서버 컴포넌트가 자기가 필요로 하는애를 각자 fetch해오면 되서 props drilling안해도 될지

데이터 캐시
- fetch로 불러온 내용을 Next서버에 보관하는 기능 (axios나 이런애는 안된다이 )
- 두번쨰 인자로 제어
  - 'no-store' => 절대 캐싱안함 (기본값)
  - 'force-cache' => 무조건 캐싱함
  - { next: { revalidate: 10 } } => ISR과 유사하게 캐싱 
  - { next: { tags: ['a'] } } => 온디맨드 ISR과 유사

fetch(url, { cache: 'force-cache' })

리퀘스트 메모아이제이션
- 요청을 기억한다.
- 중복된 동일 요청을 하나로 묶어주는 기능 (중복된 API 요청을 막기 위해)
- 사전 렌더링 시 발생하는 중복되는 요청을 캐싱해줌
  - 렌더링 종료시 바로 소멸

- 데이터 캐시와는 다르다.
  - 목적이 fetch된 결과를 반영구적으로 저장하기 위함
  - 애는 사전렌더링 동안 중복되는 요청을 막기 위함 

기존 페이지 라우터에서는 별도의 함수를 호출하고 리턴값을 페이지 컴포넌트의 props로 전달
앱 라우터 도입되면서 서버 컴포넌트로 각 컴포넌트에서 직접 fetch
=> 각 컴포넌트가 중복된 동일요청을 하는걸 없애려고

페이지 캐싱

Full Route Cache
- Nextjs 서버에서 빌드타임에 특정페이지의 렌더링 결과를 캐싱하는 기능
- SSG랑 비슷

빌드시 페이지가 Static / Dynamic으로 분류됨
  - 접속요청 받을때마다 변화가 생기거나 데이터가 변경되는 경우 Dynamic으로 분류됨 
    - DataFetching할떄 캐싱없으면
    - 동적 함수(query, param, cookie, header )를 사용하는 경우

동적함수가 없고 데이터페칭이 없거나 DataCache를 사용하는 경우 Static으로 분류됨
- Static페이지에 풀 라우트 캐시가 적용됨

빌드타임에는 searchParams가 없다.
- build시 오류 발생가능
- 클라이언트에서만 실행되게 해야함
- <Suspense></Suspense>로 감싸셈
- useSearchParams는 비동기 hooks
