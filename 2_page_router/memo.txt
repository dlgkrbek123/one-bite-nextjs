Prefetching
- 초기 페이지 접속 이후 현재 사용자가 보고 있는 페이지에서 이동가능한 페이지의 chunk를 미리 불러옴
- 데이터를 미리 불러놓아서 페이지 이동을 빠르게 하게 하기 위함

- 페이지별 코드 스플리팅을 함
- hydration하기 위해 가져오는 번들은 초기 접속 페이지를 위한 chunk만 가져옴
- 모든 페이지의 bundle을 다 불러오면 너무 거대함 
  - hydration과정까지의 지연이 커서 상호작용가능한 시간인 TTI가 길어지게 된다.

- 개발모드에서는 동작하지 않음 (프로덕션모드)
- Link 컴포넌트로 감싸진애만 prefetching됨 (프로그래매틱은 ㄴㄴ)


- Link 컴포넌트에 prefetch에 false 지정가능
- 아래처럼 해야지 프로그래매틱도 prefetch 가능

useEffect(()=> {
  router.prefetch('/test')
},[])

장점

1. 파일시스템 기반의 간편한 페이지 라우팅을 제공
- dynamic route
  - [id] => /book/2
  - [...id] => /book/2/10 
  - [[...id]] => /book or /book/2 or /book/2/10

2. 다양한 사전 렌더링
- FCP 문제를 해결하기 위해 사전 렌더링
- SSR: 요청시마다 사전 렌더링, 최신데이터 보장, 사전렌더링 도중 API CALL이 느리면 ㅠㅠ
- SSG: 빌드타임에 사전 렌더링 생성 / 최신데이터 반영이 x / getStaticPaths + fallback
- ISR: SSG + 주기적/트리거 기반 사전렌더링 재수행 (revalidate vs on-demand)


단점
1. 페이지별 레이아웃 설정이 피곤함 (getLayout 똥꼬쇼...)
2. 데이터 페칭이 페이지 컴포넌트에 집중 (getServerSideProps, getStaticProps)
3. 불필요한 컴포넌트도 번들에 포함 (hydration할때 상호작용이 없는 컴포넌트의 번들도 포함된다)
